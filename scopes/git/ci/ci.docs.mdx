# Bit CI

Bit's **`bit ci`** commands (plus one BVM enhancement) wrap several routine Bit tasks into single-purpose scripts so your CI pipelines stay short, readable and consistent.

| Command                           | Purpose                                                    | Typical CI Stage       |
| --------------------------------- | ---------------------------------------------------------- | ---------------------- |
| [`bit ci verify`](#bit-ci-verify) | Lint + build gate on every commit                          | pre-push / commit hook |
| [`bit ci pr`](#bit-ci-pr)         | Snap + export a feature lane when a PR opens/updates       | pull-request pipeline  |
| [`bit ci merge`](#bit-ci-merge)   | Tag + export new semantic versions on merge to `main`      | merge-to-main pipeline |
| [`bit ci sync`](#bit-ci-sync)     | Reconcile lanes ⇄ branches/PRs and the main scope ⇄ `main` | webhook / push / cron  |

---

## `bit ci verify`

|                  |                                                   |
| ---------------- | ------------------------------------------------- |
| **Syntax**       | `bit ci verify`                                   |
| **What it does** | Ensures the component passes CI on every commit   |
| **Runs**         | `bit install && bit status --strict && bit build` |

### When to run

- Every commit that **is not** part of an open Pull Request (e.g. a pre-push hook).
- As an early CI job to fail fast on dependency drift or broken builds.

### Exit behaviour

The command stops at the first failing step (`status`, then `build`) and returns a non-zero exit code.

## `bit ci pr`

Export a lane to Bit Cloud whenever a Pull Request is opened or updated.

```bash
bit ci pr [--message <string>] [--build] [--lane <string>]
```

| Flag        | Shorthand | Description                                                                               |
| ----------- | --------- | ----------------------------------------------------------------------------------------- |
| `--message` | `-m`      | Changelog entry. If omitted, tries the latest Git commit message (fails if unavailable).  |
| `--build`   | `-b`      | Build locally before export. If absent, Ripple-CI builds the components.                  |
| `--lane`    | `-l`      | Explicit lane name. Falls back to the current Git branch name. Performs input validation. |

### Internal flow (fail-fast on any step)

1. **Resolve lane name**
   - From `--lane` or current Git branch.
   - If the lane doesn’t exist remotely, create it; otherwise, `bit lane checkout <lane>`.
2. **Run wrapped Bit commands**

   ```bash
   bit install
   bit status --strict
   bit lane create <lane>      # no-op if already exists
   bit snap --message "<msg>" --build
   bit export
   ```

3. **Clean-up**

   ```bash
   bit lane switch main   # leaves .bitmap unchanged in the working tree
   ```

### Typical CI placement

Run on the _pull-request_ event after tests but before any deploy step.

## `bit ci merge`

Publishes new semantic versions after a PR merges to `main`.

```bash
bit ci merge [--message <string>] [--build] [--increment <level>] [--patch|--minor|--major] [--increment-by <number>]
```

| Flag                   | Shorthand | Description                                                                                                         |
| ---------------------- | --------- | ------------------------------------------------------------------------------------------------------------------- |
| `--message`            | `-m`      | Changelog entry (defaults to last Git commit message).                                                              |
| `--build`              | `-b`      | Build locally (otherwise Ripple-CI does it). Required if workspace contains _soft-tagged_ components.               |
| `--strict`             | `-s`      | Fail on warnings as well as errors (default: only fails on errors).                                                 |
| `--increment`          | `-l`      | Version bump level: `major`, `premajor`, `minor`, `preminor`, `patch`, `prepatch`, `prerelease` (default: `patch`). |
| `--patch`              | `-p`      | Shortcut for `--increment patch`.                                                                                   |
| `--minor`              |           | Shortcut for `--increment minor`.                                                                                   |
| `--major`              |           | Shortcut for `--increment major`.                                                                                   |
| `--pre-release`        |           | Shortcut for `--increment prerelease` with optional identifier.                                                     |
| `--prerelease-id`      |           | Prerelease identifier (e.g. "dev" to get "1.0.0-dev.1").                                                            |
| `--increment-by`       |           | Increment by more than 1 (e.g. `--increment-by 2` with patch: 0.0.1 → 0.0.3).                                       |
| `--auto-tag-increment` |           | Version bump level for auto-tagged dependents. See below.                                                           |

### Bumping Dependents

The version flags above apply only to the components that actually changed. Dependents that are
picked up by auto-tag are bumped by a `patch`, regardless of `--major`/`--minor`:

```bash
# button 1.0.0 -> 2.0.0, but its dependent lib 1.0.0 -> 1.0.1
bit ci merge --major
```

The one exception is a pre-release `--increment` (`prepatch`, `prerelease`, `preminor`,
`premajor`), which the dependents do follow:

```bash
# button 1.0.0 -> 1.0.1-0, and its dependent lib 1.0.0 -> 1.0.1-0 too
bit ci merge --increment prerelease
```

Use `--auto-tag-increment` to bump the dependents by an explicit level instead. It overrides both
defaults above:

```bash
# button 1.0.0 -> 2.0.0, and its dependent lib 1.0.0 -> 2.0.0 as well
bit ci merge --major --auto-tag-increment major
```

The two levels are independent, so `--major --auto-tag-increment minor` is also valid.

**Note**: auto-tag is transitive — a dependent of a dependent is auto-tagged too. So
`--auto-tag-increment major` bumps the _entire_ dependents graph by a major, not just the direct
dependents. It cannot be combined with `--skip-auto-tag`.

### Automatic Version Bump Detection

When **no explicit version flags** are provided, `bit ci merge` can automatically determine the version bump level from the commit message:

1. **Explicit Keywords** (highest priority):

   - `BIT-BUMP-MAJOR` anywhere in commit message → major version bump
   - `BIT-BUMP-MINOR` anywhere in commit message → minor version bump

2. **Conventional Commits** (when enabled):

   - `feat!:` or `BREAKING CHANGE` → major version bump
   - `feat:` → minor version bump
   - `fix:` → patch version bump

3. **Default**: patch version bump

**Note**: Auto-detection only occurs when no version flags (`--patch`, `--minor`, `--major`, etc.) are provided. Explicit flags always take precedence. `--auto-tag-increment` is not considered a version flag for this purpose — it only affects dependents, so it can be combined with auto-detection.

### Internal flow

1. **Ensure main lane**

   ```bash
   bit lane switch main   # preserves working tree files
   ```

2. **Tag, build, export**

   ```bash
   bit install
   bit tag --message "<msg>" --build --persist   # --persist only if soft tags exist
   bit export
   ```

3. **Archive remote lane** (house-keeping).
4. **Commit lock-file updates**

   ```bash
   git add .bitmap pnpm-lock.yaml
   git commit -m "chore(release): sync bitmap + lockfile"
   ```

### Version bump examples

```bash
# Explicit version bump (takes precedence over auto-detection)
bit ci merge --minor --message "feat: add new API endpoint"
bit ci merge --major --message "feat!: breaking API changes"
bit ci merge --patch --increment-by 3 --message "fix: critical patches"

# Automatic detection from commit message (no flags needed)
git commit -m "feat: add new API endpoint"
bit ci merge --build  # → auto-detects minor bump

git commit -m "feat!: breaking API changes"
bit ci merge --build  # → auto-detects major bump

git commit -m "fix: resolve memory leak"
bit ci merge --build  # → auto-detects patch bump (if conventional commits enabled)

# Using explicit keywords for auto-detection
git commit -m "feat: add new feature BIT-BUMP-MINOR"
bit ci merge --build  # → auto-detects minor bump

git commit -m "refactor: major code restructure BIT-BUMP-MAJOR"
bit ci merge --build  # → auto-detects major bump

# Default patch increment (when no detection rules match)
git commit -m "chore: update dependencies"
bit ci merge --build  # → defaults to patch bump

# Prerelease increment (explicit flag required)
bit ci merge --pre-release dev --message "feat: experimental feature"
```

### CI hint

Gate this step behind a branch-protection rule so only fast-forward merges trigger a release.

## `bit ci sync`

Keeps Bit lanes and git branches/PRs converged, in both directions, and proposes a PR when the main
scope moves ahead of the repository. The PR half goes through a pluggable git host provider — GitHub
is built in; see [Git host providers](#git-host-providers).

### Onboarding

```bash
bit ci sync --init
```

One command sets up everything `bit ci sync` needs in this repository:

- Scaffolds `.github/workflows/bit-sync.yml` and `.github/workflows/bit-release.yml`, with this
  repository's **actual default branch** substituted into them (detected the same way the reconciler
  itself detects it — `git symbolic-ref refs/remotes/origin/HEAD`, falling back to `origin/main` /
  `origin/master`). It never overwrites a file that already exists — printing a "skipped" note for it
  instead — so re-running `--init` after hand-editing either file, or after fixing just one of them, is
  safe.
- Adds `"teambit.git/ci": { "sync": {} }` to `workspace.jsonc` if that key isn't configured yet, using
  the same comment-preserving write path other aspects use to patch `workspace.jsonc` — existing keys
  and comments elsewhere in the file are left alone. Already-configured `sync` settings are never
  touched.
- Prints a checklist of what still needs a human: the `BIT_CONFIG_ACCESS_TOKEN` secret (required) and
  optional `BIT_SYNC_GH_TOKEN` PAT, a note that both scaffolded workflows already declare the
  `permissions` they need, the bit.cloud webhook recipe (the "Components → Export succeeded" event, the
  `…/dispatches` URL with this repository's owner/repo filled in when it could be read from the `origin`
  remote, the required headers, and the exact custom payload template) together with a warning that
  **editing an existing webhook drops its custom headers** (a known bit.cloud platform bug — delete and
  recreate it instead), and a reminder that checkouts need `fetch-depth: 0`.

`--init` only scaffolds and exits — it never reconciles, and cannot be combined with a lane argument or
any other flag (`--branch`, `--all`, `--main`, `--dry-run`).

```bash
bit ci sync [lane] [--branch <branch>] [--all] [--main] [--dry-run] [--init]
```

| Flag        | Description                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| ----------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| _(no args)_ | Same as `--all`: reconcile every mapped lane, then the main scope.                                                                                                                                                                                                                                                                                                                                                                                                                            |
| `[lane]`    | Reconcile a single lane — either a lane name (hosted on the workspace's `defaultScope`) or a scope-qualified lane id, `other-org.other-scope/my-lane`, for a lane hosted on another scope (see [cross-scope lanes](#cross-scope-lanes)). Validated against the `lanes` patterns in the config, which match the lane **name**. A lane that no longer exists is a no-op unless its branch carries sync history naming it — see [which branches may be retired](#which-branches-may-be-retired). |
| `--branch`  | Resolve the lane from a git branch name via the mapping config. Used by push-triggered pipelines.                                                                                                                                                                                                                                                                                                                                                                                             |
| `--all`     | Reconcile every mapped lane plus the main scope — including lanes that only still exist as a branch, so a lane deleted on bit.cloud gets its branch and PR retired. Cannot be combined with `[lane]` or `--main`.                                                                                                                                                                                                                                                                             |
| `--main`    | Reconcile only the main scope against the default branch (opens a sync PR on drift). Conflicts between the repository and the scope are resolved **in favour of the scope** (`bit checkout head --auto-merge-resolve theirs`) — see below.                                                                                                                                                                                                                                                    |
| `--dry-run` | Report the action that _would_ be taken per target. Nothing is pushed and no pull request is created, closed, labelled or commented on. It is not a read-only operation locally: the working tree, `.bitmap` and the local scope are written and then restored, and `--dry-run --main` can leave a local `<mainSyncBranch>` branch behind (the next run resets it from `origin`).                                                                                                             |
| `--init`    | One-command onboarding — see [Onboarding](#onboarding) above. Scaffolds the two workflow files and the `sync` config block, prints the remaining manual-steps checklist, and exits. Cannot be combined with `[lane]` or any other flag.                                                                                                                                                                                                                                                       |

### It is a reconciler, not a pipeline

The command is **stateless and idempotent**: it derives what to do from the current state of the lane
and of the branch, so re-running it on a converged pair is a no-op. Whatever triggers it — a bit.cloud
webhook, a `push` event, a cron schedule — only decides _when_ it runs, never _what_ it does.

### Repository checkout requirements

The reconciler reads git history and compares refs. Two different things can be missing from a checkout —
**history** and **refs** — and only one of them is a requirement:

- **Full history is required.** On GitHub Actions that means `actions/checkout` with `fetch-depth: 0`. A
  `--depth=1` (shallow) clone is **not supported**: the branch's state is the `.bitmap` at the newest commit
  on its own first-parent line that changed that file, and the dev-commit count is a revision range measured
  from that commit — neither is answerable from a truncated history, and a branch that has been synced many
  times reads as never-synced. Fetching more refs cannot help here: the commits were never transferred.
- **A narrowed refspec is fine.** A single-branch clone (`git clone --single-branch`,
  `git remote set-branches`, a mirror, or an `actions/checkout` whose refspec names one branch) **is
  supported**: every fetch the sync performs passes `+refs/heads/*:refs/remotes/origin/*` on the command
  line, and git ignores the configured `remote.origin.fetch` when a refspec is given explicitly. So the run
  populates `refs/remotes/origin/<branch>` for every branch `origin` has, however the clone was narrowed —
  which it must, because `--all` reconciles every mapped lane and every lane-mapped branch, and the
  main-scope path needs both the default branch and `<mainSyncBranch>`. The cost is that of an ordinary
  full fetch.
- **A cold local scope is fine.** The reconciler is designed for an ephemeral runner: it imports the lane
  objects it needs, and reads every piece of branch state from git and `.bitmap` rather than from whatever
  the local scope happens to have cached. `bit init` on a fresh clone is a supported starting state.

In short: **depth matters, breadth does not.** Keep `fetch-depth: 0`; `--single-branch` no longer needs
undoing.

### Which targets an `--all` run visits

The lanes to reconcile are the **union** of two sources:

1. every lane on the default scope's remote that the `lanes` patterns match, and
2. every lane-mapped branch on `origin` (`branchPrefix` / `branches` resolved in reverse) that those same
   patterns match.

The second source is what makes cleanup possible at all: a lane that was **merged, archived or deleted**
on bit.cloud is gone from the first list, so a lane-only enumeration would never visit its branch and the
`close-pr` action would never fire — every retired lane would leave an orphan branch and an open PR
behind. The default branch and `<mainSyncBranch>` are never treated as lane-mapped. Duplicates are
collapsed by lane name, so a lane that appears in both sources is reconciled once.

### Which branches may be retired

With the default `branchPrefix: ""` every branch name maps to a same-named lane, so a developer branch that
never had a lane is enumerated too — and it reaches the reconciler in the same shape as a lane branch whose
lane was just deleted, whose action (`close-pr`) **deletes the branch**. Retiring is therefore gated on how
good the command's claim on the branch is, judged from git history alone:

1. **Attribution — the branch's `.bitmap` must point at this lane.** The `.bitmap` committed on the branch
   carries bit's own lane pointer, scope-qualified, and it has to name the lane being reconciled. This is
   structural: it survives a git host rewriting commit messages on squash-merge, and no one can produce it by
   writing text into a message. A pointer bit marked **not exported** does not count — `bit lane create`
   writes one before the lane has been pushed anywhere, and a lane that was never exported cannot have been
   "removed from the remote".
2. **Reachability — deleting must not lose commits.** Either the commit that wrote that `.bitmap` is **not**
   in the default branch yet (a live lane branch of ours) _and nothing was committed on top of it_, or the
   branch **tip** already is in the default branch (everything on the branch is in the default branch, so
   deletion loses nothing). A live lane branch carrying dev commits above its state commit is never deleted:
   the PR was never merged, so that work reached neither the lane nor the default branch and exists in no
   other ref.
3. **Authorship — the reconciler must have written the branch tip.** For the live-branch case only, the tip
   must carry the `[bit-sync]` marker on a line of its own. This is the one place a commit message is
   consulted for anything but display, and it is deliberate: `.bitmap` is a file a **developer** can commit
   too. `bit create`, an unexported `bit snap` or `bit deps set` all rewrite it, so a developer's own commit
   can satisfy both tests above while carrying work that exists nowhere else. The marker is necessary but
   never sufficient — it can only ever withhold a deletion, never authorize one — and it is not required for
   the already-merged case, where reachability alone proves nothing can be lost.

The outcomes:

| Branch                                                                                      | Outcome                                                                                                 |
| ------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| `.bitmap` names this lane, not yet in the default branch, tip is our own sync commit        | PR closed, branch deleted                                                                               |
| same, but with dev commits on top                                                           | PR closed, **branch kept** — those commits reached neither the lane nor the default branch              |
| same, but the tip is a commit **we** did not write                                          | PR closed, **branch kept** — a developer wrote the branch's current state, so it may exist nowhere else |
| `.bitmap` names this lane, branch tip already in the default branch                         | PR closed, branch deleted (the just-merged lane whose branch the host didn't auto-delete)               |
| `.bitmap` names this lane and its commit is merged, but the tip is **not**                  | PR closed, **branch kept** — commits were pushed after the merge and exist in no other ref              |
| no lane pointer, one naming a different lane, an unexported one, or an unreadable `.bitmap` | `noop (branch maps to no lane and has no sync history of its own; ignoring)` — nothing written at all   |

A **kept** branch stays visible to the reconciler: every later run re-reports `close-pr` for it until the
branch is deleted by hand (or its commits reach the default branch, which makes it deletable). That is
idempotent — the first run closes the PR, and after that there is nothing left to write.

Set a `branchPrefix` (or an explicit `lanes` list) if you would rather the reconciler not enumerate those
branches at all.

### Per-lane reconciliation

For each mapped lane it compares the lane's remote head against the state recorded on the branch — the
lane's components at the versions the branch's committed `.bitmap` gives them — and picks exactly one action:

| Situation                                       | Action           | Effect                                                                         |
| ----------------------------------------------- | ---------------- | ------------------------------------------------------------------------------ |
| lane moved, branch didn't                       | `import-lane`    | Materializes the lane onto the branch, pushes, opens the PR if missing.        |
| branch got dev commits, lane didn't move        | `export-branch`  | Snaps + exports the branch's tree onto the lane, records the new head.         |
| both moved                                      | `merge-diverged` | `bit checkout head --manual` into the branch's tree, then snap + export.       |
| lane removed on bit.cloud, branch is ours       | `close-pr`       | Closes the PR; deletes the branch unless it holds unmerged commits.            |
| no lane, and the branch is not ours             | `noop`           | Nothing — see [which branches may be retired](#which-branches-may-be-retired). |
| nothing moved / PR labelled `bit-sync-conflict` | `noop`           | Nothing.                                                                       |

A lane that cannot be reconciled automatically (merge conflicts, a failing build, a stale lane) is
**halted**: the PR gets a `bit-sync-conflict` label plus a comment with resolution steps, the remaining
lanes are still synced, and the command exits non-zero. Remove the label to resume syncing that lane.
The isolation is unconditional — a lane that fails in a way nobody anticipated is halted too, never
allowed to abort the lanes after it.

### Cross-scope lanes

A lane has **two** scope relations, and they are not the same thing:

- the scope that **hosts** it — administrative, where the lane object lives (`other-org.other-scope/my-lane`);
- the scopes its **components** belong to — which repositories the change actually touches.

A lane is an org-global change set, so it can legitimately carry components from several scopes, i.e. map
to branches and PRs in several repositories. **This version of `bit ci sync` supports exactly one of those
shapes:**

> **v1 boundary.** A lane's **content must live in a single scope** — this workspace's `defaultScope`. The
> **hosting scope may differ**, and such a lane is addressable by its scope-qualified id.

```bash
bit ci sync my-lane                       # hosted on this workspace's defaultScope
bit ci sync other-org.other-scope/my-lane # hosted elsewhere, content still in this repo's scope
```

The branch mapping always uses the lane **name** (`branchPrefix` / `branches` are applied to the name), so a
foreign-hosted lane mirrors onto the same branch it would if this scope hosted it. Everything addressed to
Bit — reading the lane, snapping, exporting, and the lane pointer bit writes into the branch's `.bitmap`,
which is what attributes the branch to that lane on the next run — uses the lane's real `hostScope/name` id.

**A lane with components outside `defaultScope` is never mirrored.** The reconciler treats a lane as a whole:
it fingerprints, materializes, snaps and exports every component on it. Mirroring a cross-scope lane here
would write another repository's components into this one, propose them in a PR nobody in their scope
reviews, and export them from this repository on the release path. So the run stops before it plans or writes
anything.

But a cross-scope lane is a **legitimate thing to create** on bit.cloud — it is not a failure of this
repository. What the reconciler reports therefore depends on how it arrived at the lane. The check itself
runs on **every** trigger; only the reporting differs:

| How the lane was reached                                                   | Outcome   | Exit | PR touched                         |
| -------------------------------------------------------------------------- | --------- | ---- | ---------------------------------- |
| **Enumerated** — `--all`, or a push/webhook-triggered `--branch` reconcile | `skipped` | 0    | no                                 |
| **Explicitly named** — `bit ci sync my-lane`                               | refusal   | ≠ 0  | no                                 |
| **Became cross-scope while this repo was actively mirroring it**           | `HALTED`  | ≠ 0  | yes — labelled and commented, once |

```
# enumerated: a healthy, green run that simply has nothing to do for this lane
my-lane -> skipped (cross-scope lane: components from scope(s) other.scope (this repo maps scope
acme.shop); foreign components: other.scope/comp2 — no branch created; see the docs' Cross-scope lanes section)
```

The skip is deliberately **not** a failure: a cron or webhook run that keeps meeting a standing cross-scope
lane must stay green, or the pipeline goes permanently red over a lane that is doing nothing wrong. An
explicitly named lane is different — the user asked for that lane and must learn why nothing happened — so it
exits non-zero, but as a plain refusal, not as a sync conflict: no PR is labelled and nothing is written, so
no _future_ run behaves differently either. A branch of that name may nevertheless already exist — someone
else's, or one this repository mirrored before the lane grew a foreign component — and the message says which
of the two happened (`No branch was created and nothing was written` / `Nothing was written; the existing
branch <b> was left untouched`) rather than promising more than it did.

The **mid-flight** case is the one true halt: the branch is this lane's **live mirror** and the lane has since
grown a foreign component — so an open PR and any dev commits on that branch can never converge again. It is
annotated the usual way (`bit-sync-conflict` label plus a comment), leaves the other lanes in the run to be
reconciled, and exits non-zero. Like every other halt it **self-suppresses**: once the PR carries the
`bit-sync-conflict` label the lane is a no-op, so a scheduled run cannot re-comment on it forever. Remove the
label to hear about it again.

"Live mirror" is a stronger claim than "the branch's `.bitmap` names this lane", and the difference matters:
a squash-, rebase- or fast-forward-merged sync PR leaves the `.bitmap` it wrote on the **default branch's own
first-parent line**, so every branch cut from the default branch afterwards inherits it. The reconciler
therefore also requires that the commit which wrote that `.bitmap` is **not yet contained in the default
branch** — the same `own-live` evidence that gates branch deletion
(see [which branches may be retired](#which-branches-may-be-retired)). A branch that merely shares the lane's
name, or carries inherited state, is never labelled and never touched.

There is no flag to override any of the three.

Two consequences worth knowing:

- **`--all` does not enumerate foreign-hosted lanes.** It visits this scope's own lanes and this repository's
  lane-mapped branches; a lane hosted elsewhere is explicit-target only. (Its branch, if it has one here, is
  reached by name and reads as "not ours" — so it is left alone, never retired.)
- **Branch-derived targeting assumes `defaultScope`.** `--branch` has only a branch name to work from, so it
  resolves the lane against `defaultScope`. For a foreign-hosted lane that lookup finds nothing and the
  branch's sync history names a different lane id, which the reconciler reads as "not our branch" — a no-op.
  Safe, but it means a foreign-hosted lane must be re-targeted by its full id.

Two refusals fall out of the same "the branch mapping is keyed on the lane **name**" fact, and both are
checked before anything is planned:

- **Two lanes, one branch.** `other.scope/release` and `<defaultScope>/release` map to the same branch. If the
  branch is the **live mirror** of one of them, reconciling the other is a halt
  (`branch release mirrors lane other.scope/release; refusing to plan for …`) rather than a hijack — an
  `import-lane` would otherwise materialize the second lane over the first one's content and repoint the
  branch's `.bitmap` at it. The check only applies when the lane being reconciled actually exists: with no lane
  there is nothing to write, and the one destructive action left (`close-pr`) already refuses without
  attribution to that lane.

  Note **whose PR gets labelled**: the branch's owner's. The refused lane has no PR of its own, so the
  `bit-sync-conflict` label lands on a pull request whose own lane is perfectly healthy, and freezes its
  syncs until a human removes it. That is the right trade — two lanes contending for one branch needs a
  person either way, and the alternative is one silently overwriting the other — but it is why the comment
  posted there names both lanes, says the PR's own lane is fine, and explicitly tells the reader **not** to
  run the usual `bit lane import` steps (they would perform the overwrite the halt just refused). Resolve it
  by renaming one lane or mapping one of them elsewhere with `branches`. Under `--dry-run` nothing is
  labelled or commented at all.

- **Reserved branches.** A `branches` override (or a lane named after the default branch) can map a lane onto
  the default branch or `<mainSyncBranch>`. Those belong to the main-scope path, which never writes to the
  default branch directly, so the lane path refuses them — skipped when enumerated, a refusal when named
  explicitly. This is enforced inside the per-lane reconciler, so `--all` is covered too.

**Known gap in the collision check.** It fires only while the branch is the other lane's **live** mirror. Once
that lane's sync PR has been merged and further commits pushed to the branch (`own-superseded`), the branch is
no longer anybody's live mirror, and a same-named lane reconciled against it will read the _other_ lane's
recorded component versions as its own last-synced state and plan from there. This is pre-existing behaviour,
not introduced by the collision check, and it is left alone on purpose: tightening it means treating an
inherited `.bitmap` as a claim, which is precisely what gets ordinary developer branches labelled. Give
colliding lanes distinct names or distinct `branches` entries.

Support for lanes that genuinely span scopes is designed in two later stages: **Stage 1** slices a lane by
scope (per-repository fingerprint, materialization, export and PR, plus a `laneSources` config so foreign-hosted
lanes can be enumerated), and **Stage 2** adds the coordinated cross-repository release, which needs a
scope→repository registry and an all-PRs-merged gate before any slice merges. See the `bit-git-sync` design
document's _Cross-scope lanes_ section.

### Main-scope reconciliation

`--main` (and the tail of an `--all` run) reconciles the scope's `main` with the repository:

1. `git checkout -B <mainSyncBranch>` from the existing sync branch, or from the default branch when
   there isn't one yet. When the sync branch already existed, the default branch is then merged into it,
   so the PR stays mergeable and the drift is computed against the repository's current state.
2. `bit checkout head`, including components that exist on the scope but not yet in this workspace, and
   resolving conflicts in favour of the scope (see below).
3. An empty `git status` **is** convergence. Otherwise the drift is committed with a `[bit-sync]`
   marker, pushed to `<mainSyncBranch>` (never force-pushed), and a pull request is opened against the
   default branch.

The default branch is never written to directly — the convergence is always proposed as a PR.

**Conflict resolution is one-sided, on purpose.** The whole point of the main sync PR is to show what
the repository looks like at the scope's latest exported versions, so the checkout runs with
`--auto-merge-resolve theirs`: where a file in the repository conflicts with the exported version, the
exported version wins. If a component held source changes that were never exported to Bit, this PR
therefore **reverts** them — visibly, in the PR diff, for a human to reject by closing the PR. (The
alternative, resolving in favour of the repository, would advance `.bitmap` to the new versions while
keeping the old files — a commit asserting a state the tree does not have.)

### Git host providers

The sync engine is host-agnostic. Everything it does with git is plain git, and everything it does
with _pull requests_ goes through a `GitHostProvider` — find/create/close a PR, comment, add a label.
GitHub ships built-in and is registered by this aspect itself, through the same public slot anyone
else uses:

```ts
import type { CiMain, GitHostProvider } from '@teambit/ci';

// in your aspect's provider()
ci.registerGitHostProvider(new GitLabHostProvider());
```

Each `bit ci sync` run selects at most one provider, from the `origin` remote:

1. **A claim is exclusive.** If any registered provider claims the remote (`matchesRemote`), only a
   claimant can be selected — the first one that also has credentials (`isConfigured`). If no claimant
   is configured, the run goes PR-less and warns which provider claimed the remote; another provider is
   never used in its place, because that would create, close and comment on pull requests on the wrong
   host.
2. **A single configured provider is the fallback when nobody claims** — the remote couldn't be read, or
   no provider recognises it (a self-hosted host on a custom domain, a mirror, an `insteadOf` rewrite).
   Two or more configured providers there is ambiguous, so the run goes PR-less.

Because of (1), registering a provider never changes how a repository claimed by a _different_ provider
is handled. Whenever no provider is selected, the run says why, does all of its git and Bit work, and
skips only the pull-request operations.

### GitHub credentials

PR operations need a token, plus a repository. **`BIT_GITHUB_TOKEN` is checked first and
`GITHUB_TOKEN` second**, because the first is the override and the second is the ambient default: GitHub
Actions sets `GITHUB_TOKEN` on every job, so a `BIT_GITHUB_TOKEN` that did not outrank it could never
take effect there — which is the one place people set it, to supply a PAT with permissions the workflow
token lacks (and to make sync pushes trigger downstream CI). The repository is taken from
`GITHUB_REPOSITORY` when present, otherwise parsed from the `origin` remote. Without a token the command
still does all of its git and Bit work and logs the PR operations it skipped.

## Configuration

The CI aspect supports configuration in `workspace.jsonc`:

```json
{
  "teambit.git/ci": {
    "commitMessageScript": "node scripts/generate-commit-message.js",
    "useConventionalCommitsForVersionBump": true,
    "useExplicitBumpKeywords": true
  }
}
```

### `commitMessageScript`

**Optional.** Path to a script that generates custom commit messages for the `bit ci merge` command.

- **Default**: Uses `"chore: update .bitmap and lockfiles as needed [skip ci]"`
- **Usage**: The script should output the desired commit message to stdout
- **Security**: Commands are parsed to avoid shell injection - no chaining allowed
- **Working Directory**: Script runs in the workspace root directory

**Example script:**

```javascript
#!/usr/bin/env node
const { execSync } = require('child_process');

try {
  const version = execSync('npm show @my/package version', { encoding: 'utf8' }).trim();
  console.log(`bump version to ${version} [skip ci]`);
} catch {
  console.log('chore: update .bitmap and lockfiles as needed [skip ci]');
}
```

### `useConventionalCommitsForVersionBump`

**Optional.** Enable automatic version bump detection based on conventional commit patterns.

- **Default**: `false` (disabled)
- **When enabled**: Analyzes commit messages for conventional commit patterns:
  - `feat!:` or `BREAKING CHANGE` → major version bump
  - `feat:` → minor version bump
  - `fix:` → patch version bump

```json
{
  "teambit.git/ci": {
    "useConventionalCommitsForVersionBump": true
  }
}
```

### `useExplicitBumpKeywords`

**Optional.** Enable automatic version bump detection using explicit keywords.

- **Default**: `true` (enabled)
- **Keywords**:
  - `BIT-BUMP-MAJOR` anywhere in commit message → major version bump
  - `BIT-BUMP-MINOR` anywhere in commit message → minor version bump

```json
{
  "teambit.git/ci": {
    "useExplicitBumpKeywords": false // disable explicit keywords
  }
}
```

**Example usage:**

```bash
git commit -m "feat: add new feature BIT-BUMP-MINOR"
bit ci merge --build  # → automatically uses minor version bump
```

### `sync`

**Optional.** Lane ⇄ branch mapping and main-scope settings for [`bit ci sync`](#bit-ci-sync).

```json
{
  "teambit.git/ci": {
    "sync": {
      "mode": "git-source-of-truth",
      "branchPrefix": "lane/",
      "branches": { "design-system": "feature/design-system" },
      "lanes": ["*"],
      "mainSyncBranch": "bit-sync/main",
      "autoMergeMainSyncPr": false
    }
  }
}
```

| Field                 | Default               | Description                                                                                                                                                                                                                                                                                                                                   |
| --------------------- | --------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `mode`                | `git-source-of-truth` | **Reserved: accepted but not implemented** — every run behaves as `git-source-of-truth`, and the command warns when another value is configured. Intended semantics: `git-source-of-truth` (today's behaviour) keeps merges on the git host and mirrors lanes to PRs; `mirror` would allow merges on bit.cloud and have git track the result. |
| `branchPrefix`        | `""`                  | Prefix for lane-mapped branches, e.g. `"lane/"` maps lane `my-lane` ⇄ branch `lane/my-lane`.                                                                                                                                                                                                                                                  |
| `branches`            | `{}`                  | Explicit lane-name → branch-name overrides; they win over `branchPrefix`.                                                                                                                                                                                                                                                                     |
| `lanes`               | `["*"]`               | Glob patterns (`*` only) of lane names to sync. `[]` disables lane mirroring entirely, leaving main-scope sync.                                                                                                                                                                                                                               |
| `mainSyncBranch`      | `"bit-sync/main"`     | Branch used for the main-scope drift PR.                                                                                                                                                                                                                                                                                                      |
| `autoMergeMainSyncPr` | `false`               | Reserved: enabling GitHub auto-merge on the sync PR is not implemented yet — the command warns if it is set. Use a repository rule.                                                                                                                                                                                                           |

The default branch and `mainSyncBranch` are never treated as lane-mapped, even when `branchPrefix` is
empty (which otherwise maps every branch to a same-named lane).
