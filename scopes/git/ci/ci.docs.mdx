# Bit CI

Bit's **`bit ci`** commands (plus one BVM enhancement) wrap several routine Bit tasks into single-purpose scripts so your CI pipelines stay short, readable and consistent.

| Command                           | Purpose                                                    | Typical CI Stage       |
| --------------------------------- | ---------------------------------------------------------- | ---------------------- |
| [`bit ci verify`](#bit-ci-verify) | Lint + build gate on every commit                          | pre-push / commit hook |
| [`bit ci pr`](#bit-ci-pr)         | Snap + export a feature lane when a PR opens/updates       | pull-request pipeline  |
| [`bit ci merge`](#bit-ci-merge)   | Tag + export new semantic versions on merge to `main`      | merge-to-main pipeline |
| [`bit ci sync`](#bit-ci-sync)     | Reconcile lanes ⇄ branches/PRs and the main scope ⇄ `main` | webhook / push / cron  |

---

## `bit ci verify`

|                  |                                                   |
| ---------------- | ------------------------------------------------- |
| **Syntax**       | `bit ci verify`                                   |
| **What it does** | Ensures the component passes CI on every commit   |
| **Runs**         | `bit install && bit status --strict && bit build` |

### When to run

- Every commit that **is not** part of an open Pull Request (e.g. a pre-push hook).
- As an early CI job to fail fast on dependency drift or broken builds.

### Exit behaviour

The command stops at the first failing step (`status`, then `build`) and returns a non-zero exit code.

## `bit ci pr`

Export a lane to Bit Cloud whenever a Pull Request is opened or updated.

```bash
bit ci pr [--message <string>] [--build] [--lane <string>]
```

| Flag        | Shorthand | Description                                                                               |
| ----------- | --------- | ----------------------------------------------------------------------------------------- |
| `--message` | `-m`      | Changelog entry. If omitted, tries the latest Git commit message (fails if unavailable).  |
| `--build`   | `-b`      | Build locally before export. If absent, Ripple-CI builds the components.                  |
| `--lane`    | `-l`      | Explicit lane name. Falls back to the current Git branch name. Performs input validation. |

### Internal flow (fail-fast on any step)

1. **Resolve lane name**
   - From `--lane` or current Git branch.
   - If the lane doesn’t exist remotely, create it; otherwise, `bit lane checkout <lane>`.
2. **Run wrapped Bit commands**

   ```bash
   bit install
   bit status --strict
   bit lane create <lane>      # no-op if already exists
   bit snap --message "<msg>" --build
   bit export
   ```

3. **Clean-up**

   ```bash
   bit lane switch main   # leaves .bitmap unchanged in the working tree
   ```

### Typical CI placement

Run on the _pull-request_ event after tests but before any deploy step.

## `bit ci merge`

Publishes new semantic versions after a PR merges to `main`.

```bash
bit ci merge [--message <string>] [--build] [--increment <level>] [--patch|--minor|--major] [--increment-by <number>]
```

| Flag                   | Shorthand | Description                                                                                                         |
| ---------------------- | --------- | ------------------------------------------------------------------------------------------------------------------- |
| `--message`            | `-m`      | Changelog entry (defaults to last Git commit message).                                                              |
| `--build`              | `-b`      | Build locally (otherwise Ripple-CI does it). Required if workspace contains _soft-tagged_ components.               |
| `--strict`             | `-s`      | Fail on warnings as well as errors (default: only fails on errors).                                                 |
| `--increment`          | `-l`      | Version bump level: `major`, `premajor`, `minor`, `preminor`, `patch`, `prepatch`, `prerelease` (default: `patch`). |
| `--patch`              | `-p`      | Shortcut for `--increment patch`.                                                                                   |
| `--minor`              |           | Shortcut for `--increment minor`.                                                                                   |
| `--major`              |           | Shortcut for `--increment major`.                                                                                   |
| `--pre-release`        |           | Shortcut for `--increment prerelease` with optional identifier.                                                     |
| `--prerelease-id`      |           | Prerelease identifier (e.g. "dev" to get "1.0.0-dev.1").                                                            |
| `--increment-by`       |           | Increment by more than 1 (e.g. `--increment-by 2` with patch: 0.0.1 → 0.0.3).                                       |
| `--auto-tag-increment` |           | Version bump level for auto-tagged dependents. See below.                                                           |

### Bumping Dependents

The version flags above apply only to the components that actually changed. Dependents that are
picked up by auto-tag are bumped by a `patch`, regardless of `--major`/`--minor`:

```bash
# button 1.0.0 -> 2.0.0, but its dependent lib 1.0.0 -> 1.0.1
bit ci merge --major
```

The one exception is a pre-release `--increment` (`prepatch`, `prerelease`, `preminor`,
`premajor`), which the dependents do follow:

```bash
# button 1.0.0 -> 1.0.1-0, and its dependent lib 1.0.0 -> 1.0.1-0 too
bit ci merge --increment prerelease
```

Use `--auto-tag-increment` to bump the dependents by an explicit level instead. It overrides both
defaults above:

```bash
# button 1.0.0 -> 2.0.0, and its dependent lib 1.0.0 -> 2.0.0 as well
bit ci merge --major --auto-tag-increment major
```

The two levels are independent, so `--major --auto-tag-increment minor` is also valid.

**Note**: auto-tag is transitive — a dependent of a dependent is auto-tagged too. So
`--auto-tag-increment major` bumps the _entire_ dependents graph by a major, not just the direct
dependents. It cannot be combined with `--skip-auto-tag`.

### Automatic Version Bump Detection

When **no explicit version flags** are provided, `bit ci merge` can automatically determine the version bump level from the commit message:

1. **Explicit Keywords** (highest priority):

   - `BIT-BUMP-MAJOR` anywhere in commit message → major version bump
   - `BIT-BUMP-MINOR` anywhere in commit message → minor version bump

2. **Conventional Commits** (when enabled):

   - `feat!:` or `BREAKING CHANGE` → major version bump
   - `feat:` → minor version bump
   - `fix:` → patch version bump

3. **Default**: patch version bump

**Note**: Auto-detection only occurs when no version flags (`--patch`, `--minor`, `--major`, etc.) are provided. Explicit flags always take precedence. `--auto-tag-increment` is not considered a version flag for this purpose — it only affects dependents, so it can be combined with auto-detection.

### Internal flow

1. **Ensure main lane**

   ```bash
   bit lane switch main   # preserves working tree files
   ```

2. **Tag, build, export**

   ```bash
   bit install
   bit tag --message "<msg>" --build --persist   # --persist only if soft tags exist
   bit export
   ```

3. **Archive remote lane** (house-keeping).
4. **Commit lock-file updates**

   ```bash
   git add .bitmap pnpm-lock.yaml
   git commit -m "chore(release): sync bitmap + lockfile"
   ```

### Version bump examples

```bash
# Explicit version bump (takes precedence over auto-detection)
bit ci merge --minor --message "feat: add new API endpoint"
bit ci merge --major --message "feat!: breaking API changes"
bit ci merge --patch --increment-by 3 --message "fix: critical patches"

# Automatic detection from commit message (no flags needed)
git commit -m "feat: add new API endpoint"
bit ci merge --build  # → auto-detects minor bump

git commit -m "feat!: breaking API changes"
bit ci merge --build  # → auto-detects major bump

git commit -m "fix: resolve memory leak"
bit ci merge --build  # → auto-detects patch bump (if conventional commits enabled)

# Using explicit keywords for auto-detection
git commit -m "feat: add new feature BIT-BUMP-MINOR"
bit ci merge --build  # → auto-detects minor bump

git commit -m "refactor: major code restructure BIT-BUMP-MAJOR"
bit ci merge --build  # → auto-detects major bump

# Default patch increment (when no detection rules match)
git commit -m "chore: update dependencies"
bit ci merge --build  # → defaults to patch bump

# Prerelease increment (explicit flag required)
bit ci merge --pre-release dev --message "feat: experimental feature"
```

### CI hint

Gate this step behind a branch-protection rule so only fast-forward merges trigger a release.

## `bit ci sync`

Keeps Bit lanes and git branches/PRs converged in both directions, and proposes a pull request when the main
scope moves ahead of the repository. Pull-request operations go through a pluggable git host provider;
GitHub is built in.

It is a **reconciler, not a pipeline** — stateless and idempotent, deriving what to do from the current state
of the lane and of the branch. Re-running it on a converged pair is a no-op, and the trigger only decides
_when_ it runs, never _what_ it does.

### Onboarding

```bash
bit ci sync --init
```

`--init` scaffolds `.github/workflows/bit-sync.yml` and `bit-release.yml` with this repository's real
default branch substituted in, adds `"teambit.git/ci": { "sync": {} }` to `workspace.jsonc` if absent
(comment-preserving; existing `sync` settings are untouched), and prints what still needs a human: the
`BIT_CONFIG_ACCESS_TOKEN` secret, the optional `BIT_SYNC_GH_TOKEN` PAT, the bit.cloud webhook recipe, and a
`fetch-depth: 0` reminder. Existing files are reported as skipped, never overwritten, so re-running is safe.
It only scaffolds, then exits — it cannot be combined with a lane argument or any other flag.

> **bit.cloud platform bug:** editing an existing webhook silently drops its custom headers. Delete the
> webhook and recreate it rather than editing it.

### Usage

```bash
bit ci sync [lane] [--branch <branch>] [--all] [--main] [--dry-run] [--init]
```

| Flag        | Description                                                                                                                                                                                               |
| ----------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| _(no args)_ | Same as `--all`.                                                                                                                                                                                          |
| `[lane]`    | One lane, by name (hosted on `defaultScope`) or by scope-qualified id (`other-org.other-scope/my-lane`). Still filtered by the `lanes` patterns, which match the lane **name**.                           |
| `--branch`  | Resolve the lane from a branch name through the mapping config — for push-triggered runs. Has only a branch name to work from, so it assumes `defaultScope`.                                              |
| `--all`     | Every mapped lane plus the main scope, including lanes that only still exist as a branch, so a lane deleted on bit.cloud gets its branch and PR retired.                                                  |
| `--main`    | Only the main scope, against the default branch.                                                                                                                                                          |
| `--dry-run` | Report the action each target _would_ get; nothing is pushed and no PR is created, closed, labelled or commented. Not read-only locally — the tree, `.bitmap` and local scope are written, then restored. |
| `--init`    | Onboarding, above. Cannot be combined with anything else.                                                                                                                                                 |

### Triggers

Any trigger works, because the command is a reconciler. The scaffolded workflow wires the three that
matter: a bit.cloud webhook for "a lane moved", a `push` for "a branch moved", and a cron safety net.

```yaml
name: bit-sync
on:
  repository_dispatch: { types: [bit-lane-updated] }
  push: { branches-ignore: ['bit-sync/**'] }
  schedule: [{ cron: '0 * * * *' }]
permissions: { contents: write, pull-requests: write }
jobs:
  sync:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with: { fetch-depth: 0 } # full history is required
      - run: npx @teambit/bvm install && bit ci sync
        env:
          BIT_CONFIG_ACCESS_TOKEN: ${{ secrets.BIT_CONFIG_ACCESS_TOKEN }}
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
```

**Depth matters, breadth does not.** Full history (`fetch-depth: 0`) is required — a branch's state is the
`.bitmap` at the newest commit on its own first-parent line that touched it, which a shallow clone cannot
answer. A narrowed refspec and a cold local scope are both fine.

### Per-lane reconciliation

For each mapped lane it compares the lane's remote head with the state the branch's committed `.bitmap`
records, and picks exactly one action:

| Situation                                       | Action           | Effect                                                                         |
| ----------------------------------------------- | ---------------- | ------------------------------------------------------------------------------ |
| lane moved, branch didn't                       | `import-lane`    | Materializes the lane onto the branch, pushes, opens the PR if missing.        |
| branch got dev commits, lane didn't move        | `export-branch`  | Snaps + exports the branch's tree onto the lane.                               |
| both moved                                      | `merge-diverged` | Merges the lane into the branch's tree, then snaps + exports.                  |
| lane removed on bit.cloud, branch is ours       | `close-pr`       | Closes the PR; deletes the branch unless it holds unmerged commits.            |
| no lane, and the branch is not ours             | `noop`           | Nothing — see [which branches may be retired](#which-branches-may-be-retired). |
| nothing moved / PR labelled `bit-sync-conflict` | `noop`           | Nothing.                                                                       |

An `--all` run visits the **union** of the lanes matching the `lanes` patterns and the lane-mapped branches on
`origin`. The second source is what makes cleanup possible: a lane deleted on bit.cloud is gone from the
first list, so a lane-only enumeration would leave an orphan branch and an open PR behind.

### Halts and conflicts

A lane that cannot be reconciled automatically is **halted**: its PR gets a `bit-sync-conflict` label plus a
comment with resolution steps, the remaining lanes still sync, and the command exits non-zero. Halting is
per-lane and unconditional — an unanticipated failure never aborts the lanes after it — and it
**self-suppresses**: while the label is on the PR that lane is a no-op. Remove the label to resume.

`onConflict` decides what `merge-diverged` does when the lane and the branch changed the same lines:

- `"halt"` (the default) stops that lane as above. Either alternative rewrites one side's work without
  review, so silence is opt-in.
- `"git-wins"` / `"lane-wins"` resolve the conflicting hunks to the branch's or the lane's version, then
  continue through the normal merge-diverged tail. Resolution is at component granularity: every file of a
  conflicted component takes the winning side.

Non-conflicting hunks always merge whichever policy is set, and the summary names what it rewrote.

### Which branches may be retired

With the default empty `branchPrefix` every branch maps to a same-named lane, so developer branches are
enumerated too — reaching the reconciler in the same shape as a lane branch whose lane was deleted, whose
action deletes the branch. Deletion is therefore gated on three tests, judged from git history alone:

1. **Attribution** — the branch's committed `.bitmap` must carry bit's own scope-qualified pointer to _this_
   lane. Being structural, it survives squash-merge message rewrites; a pointer bit marked **not exported**
   does not count, since that lane was never on any remote.
2. **Reachability** — either that state commit is not in the default branch yet _and_ nothing was committed
   on top of it, or the branch **tip** is already in the default branch, so deleting loses nothing.
3. **Authorship** — for the live-branch case, the tip must carry the `[bit-sync]` marker on its own line.
   `.bitmap` is a file developers commit too, so this is necessary but never sufficient: it can only
   withhold a deletion, never authorize one.

Failing attribution is a plain `noop`, writing nothing. A **kept** branch is re-reported on every later run
until it is deleted by hand or its commits reach the default branch — idempotent, since the PR was closed on
the first run. Set a `branchPrefix` or an explicit `lanes` list to keep developer branches out entirely.

### Cross-scope lanes

A lane's **hosting** scope (where the lane object lives) and its **components'** scopes (which repositories
the change touches) are different things. This version supports exactly one shape: a lane's content must
live in a single scope — this workspace's `defaultScope` — while the hosting scope may differ, and such a
lane is addressable by its scope-qualified id.

```bash
bit ci sync my-lane                       # hosted on this workspace's defaultScope
bit ci sync other-org.other-scope/my-lane # hosted elsewhere, content still in this repo's scope
```

The branch mapping always uses the lane **name**, so a foreign-hosted lane mirrors onto the branch it would
anyway, while everything addressed to Bit uses the real `hostScope/name` id.

**A lane with components outside `defaultScope` is never mirrored** — that would write another repository's
components into this one and export them from here. Creating such a lane is legitimate, though, so only the
reporting depends on how the lane was reached:

| How the lane was reached                                     | Outcome   | Exit | PR touched                |
| ------------------------------------------------------------ | --------- | ---- | ------------------------- |
| **Enumerated** — `--all`, or a push/webhook `--branch` run   | `skipped` | 0    | no                        |
| **Explicitly named** — `bit ci sync my-lane`                 | refusal   | ≠ 0  | no                        |
| **Became cross-scope while this repo was mirroring it live** | `HALTED`  | ≠ 0  | yes — labelled, commented |

The skip is deliberately green: a standing cross-scope lane must not turn every scheduled run red. A named
lane exits non-zero so the user learns why nothing happened, but as a plain refusal — nothing written, no PR
labelled. Two lanes colliding onto one branch are refused the same way rather than one hijacking the other,
and the default branch and `mainSyncBranch` are never lane-mapped. None of this is overridable.

### Main-scope reconciliation

`--main`, and the tail of an `--all` run, reconciles the scope's `main` with the repository:

1. `git checkout -B <mainSyncBranch>` from the existing sync branch, else the default branch; an existing
   sync branch then has the default branch merged in so the PR stays mergeable.
2. `bit checkout head`, including components on the scope but not yet in this workspace, resolving conflicts
   **in favour of the scope** (`--auto-merge-resolve theirs`).
3. An empty `git status` **is** convergence. Otherwise the drift is committed with a `[bit-sync]` marker,
   pushed to `<mainSyncBranch>` (never force-pushed), and proposed as a PR against the default branch.

The one-sided resolution is the point: the PR shows the repository at the scope's latest exported versions,
so component source that was never exported is **reverted** — visibly, in the PR diff, for a human to reject
by closing the PR. Under `mainSync: "direct-push"` the same drift commit goes straight onto the default
branch — no sync branch, no PR — with a plain push, so a default branch that moved mid-run halts the run.

### Git host providers and credentials

Everything the sync does with git is plain git; everything it does with _pull requests_ goes through a
`GitHostProvider`. GitHub ships built-in, registered via `ci.registerGitHostProvider(...)` — the same public
slot anyone else uses. At most one provider is selected per run, from the `origin` remote: a provider
claiming the remote is selected exclusively (if no claimant has credentials the run goes PR-less rather than
acting on the wrong host), and a single configured provider is the fallback when nobody claims. With none
selected, the run says why, does all of its git and Bit work, and skips only the pull-request operations.

For GitHub, **`BIT_GITHUB_TOKEN` is checked before `GITHUB_TOKEN`**, since Actions sets the latter on every
job and an override that did not outrank it could never take effect. The repository comes from
`GITHUB_REPOSITORY`, otherwise from the `origin` remote.

## Configuration

The CI aspect supports configuration in `workspace.jsonc`:

```json
{
  "teambit.git/ci": {
    "commitMessageScript": "node scripts/generate-commit-message.js",
    "useConventionalCommitsForVersionBump": true,
    "useExplicitBumpKeywords": true
  }
}
```

### `commitMessageScript`

**Optional.** Path to a script that generates custom commit messages for the `bit ci merge` command.

- **Default**: Uses `"chore: update .bitmap and lockfiles as needed [skip ci]"`
- **Usage**: The script should output the desired commit message to stdout
- **Security**: Commands are parsed to avoid shell injection - no chaining allowed
- **Working Directory**: Script runs in the workspace root directory

**Example script:**

```javascript
#!/usr/bin/env node
const { execSync } = require('child_process');

try {
  const version = execSync('npm show @my/package version', { encoding: 'utf8' }).trim();
  console.log(`bump version to ${version} [skip ci]`);
} catch {
  console.log('chore: update .bitmap and lockfiles as needed [skip ci]');
}
```

### `useConventionalCommitsForVersionBump`

**Optional.** Enable automatic version bump detection based on conventional commit patterns.

- **Default**: `false` (disabled)
- **When enabled**: Analyzes commit messages for conventional commit patterns:
  - `feat!:` or `BREAKING CHANGE` → major version bump
  - `feat:` → minor version bump
  - `fix:` → patch version bump

```json
{
  "teambit.git/ci": {
    "useConventionalCommitsForVersionBump": true
  }
}
```

### `useExplicitBumpKeywords`

**Optional.** Enable automatic version bump detection using explicit keywords.

- **Default**: `true` (enabled)
- **Keywords**:
  - `BIT-BUMP-MAJOR` anywhere in commit message → major version bump
  - `BIT-BUMP-MINOR` anywhere in commit message → minor version bump

```json
{
  "teambit.git/ci": {
    "useExplicitBumpKeywords": false // disable explicit keywords
  }
}
```

**Example usage:**

```bash
git commit -m "feat: add new feature BIT-BUMP-MINOR"
bit ci merge --build  # → automatically uses minor version bump
```

### `sync`

**Optional.** Lane ⇄ branch mapping and main-scope settings for [`bit ci sync`](#bit-ci-sync).

```json
{
  "teambit.git/ci": {
    "sync": { "branchPrefix": "lane/", "lanes": ["*"], "onConflict": "halt" }
  }
}
```

| Field                 | Default                 | Description                                                                                                                                        |
| --------------------- | ----------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| `mode`                | `"git-source-of-truth"` | **Reserved** — accepted but not implemented; every run behaves as `git-source-of-truth`, and any other value warns.                                |
| `branchPrefix`        | `""`                    | Prefix for lane-mapped branches: `"lane/"` maps lane `my-lane` ⇄ branch `lane/my-lane`.                                                            |
| `branches`            | `{}`                    | Explicit lane-name → branch-name overrides; they win over `branchPrefix`.                                                                          |
| `lanes`               | `["*"]`                 | Glob patterns (`*` only) of lane names to sync; `[]` disables lane mirroring, leaving main-scope sync.                                             |
| `mainSyncBranch`      | `"bit-sync/main"`       | Branch carrying the main-scope drift PR. Unused under `mainSync: "direct-push"`.                                                                   |
| `mainSync`            | `"pr"`                  | `"pr"` proposes main-scope drift from `mainSyncBranch`; `"direct-push"` commits it straight onto the default branch.                               |
| `onConflict`          | `"halt"`                | Same-line divergence in `merge-diverged`: `"halt"` labels the PR for a human; `"git-wins"` / `"lane-wins"` resolve conflicting hunks to that side. |
| `autoMergeMainSyncPr` | `false`                 | **Reserved** — GitHub auto-merge on the sync PR is not implemented; use a repository rule.                                                         |

Branch names are validated at startup, naming the offending config key rather than failing mid-run. The
default branch and `mainSyncBranch` are never treated as lane-mapped, even with an empty `branchPrefix`.
